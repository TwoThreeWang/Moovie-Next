# 产品定位与设计决策

这份文档记录影牛为什么这样设计：产品定位、合规边界、整体架构和做过的取舍。各模块具体怎么实现，见 [README](../README.md#文档) 里列出的其他文档。

> 文中的合规判断是按常见法律逻辑做的分析，不是法律意见。

## 定位

| 项 | 决定 |
| --- | --- |
| 形态 | 网站。浏览作品资料、短评、片单、公开主页不用登录；播放、标记、发短评要登录 |
| 平台做什么 | 统一采集和整理影视**元数据**；提供观影记录、发现、片单和社区功能 |
| 平台不做什么 | 不提供、不推荐、不保存任何播放源 |
| 播放源 | 完全由用户自己填写订阅地址 |
| 平台 | 只做网页版，可以添加到手机桌面；不做 App |
| 收费 | 目前不收费 |

一句话：**平台是"元数据 + 观影记录"服务，外加一个中立的播放器；播放源由用户自带。**

## 合规边界

1. **不提供源。** 没有默认源、源推荐、源市场，也没有用户之间共享源的功能。
2. **视频不经过服务器。** 不代理、不改写、不缓存 m3u8 和分片，由浏览器直接加载。
3. **服务器上没有明文的源信息。** 订阅地址在浏览器里加密后才同步到账号；"上次用的哪个源"、资源站的 `vod_id` 只存在本机，或者在服务器解不开的加密历史里。
4. **作品库不从资源站生成。** 资源站返回的片名、简介、海报不用来建作品或补资料。
5. **不在本站执行第三方代码。** 兼容 TVBox 配置时只导入苹果 CMS 接口，不运行爬虫（jar / js / py），也不使用解析正版平台 VIP 链接的 `parses`。
6. **宣传和界面不暗示"免费看片"。**
7. **保留通知—删除机制。** 版权投诉页公布联系邮箱（`CONTACT_EMAIL`），收到投诉及时处理。

目前有两处例外，都是用户的决定：

| 例外 | 做法 | 原因 |
| --- | --- | --- |
| 播放源的查询由服务器转发 | `/api/relay` 只转发订阅文件和苹果 CMS 的查询，视频仍不经过服务器，不记录转发的地址（见 [播放源](playback.md#查询的转发)） | 2026-11-17：大多数资源站没有跨域许可，浏览器直接查询用不了。先不考虑这一点的合规影响，对外说法暂不改 |
| 临时的示例订阅 | 设置页和迁移账号填的是外部地址；本站以前的 `/sub/example.json` 跳到外部地址（见 [从已有数据初始化](bootstrap.md#临时示例订阅)） | 让早期用户有源可用，之后删除 |

### 做到以后还剩什么风险

结构上接近 Kodi、Stremio 的模式，风险从"高"降到"中"，降不到零。剩下的主要是：

- 产品整体观感：输入格式是苹果 CMS 接口、带广告跳过功能，都说明知道源是什么。
- 用户在本站的界面里完成"找片—选集—播放"全过程，国内法院可能据此认定实质替代。
- 豆瓣数据靠抓取；第三方弹幕来自别的平台（这两项是已经接受的风险）。

以后如果开始收费，要再加一条：收费功能必须和播放无关。同时要重新看资料来源的授权：TMDB 商用要签协议。

## 整体架构

```
┌───────────────── 浏览器（用户设备） ─────────────────┐
│  订阅管理 ─ 查源 ─ 解析 ─ 匹配作品 ─ 播放 ─ 广告跳过    │
│  本机存储：订阅缓存、查源结果、上次用的源、设备密钥、    │
│  加密历史的明文副本、广告指纹列表                       │
└───────┬──────────────────────────────┬──────────────┘
        │ 元数据、用户数据、               │ m3u8 和分片直连，
        │ 播放源查询的转发                 │ 服务器不参与
        ▼                              ▼
┌──── 影牛服务器 ─────────┐        ┌── 用户自己填的资源站 ──┐
│ 作品资料、账号、想看看过、 │ 转发   │ 查询接口、m3u8、分片    │
│ 播放进度、短评、片单、弹幕、│──────▶│                       │
│ 广告指纹、加密历史、密文配置│        └──────────────────────┘
└───────┬────────────────┘
        │ 服务器访问的其他外部服务
        ▼
  豆瓣、TMDB、Wikidata、红果短剧官网、AI 接口、SMTP、Telegram、第三方弹幕库
```

### 服务器上关于用户的数据

| 数据 | 形式 |
| --- | --- |
| 账号、设置、想看和看过、评分 | 明文 |
| 播放进度（作品库里有的） | 明文，只有作品 ID、季、集和进度 |
| 播放进度（作品库里没有的） | 密文，服务器解不开 |
| 订阅地址和设备密钥 | 密文，用登录密码在浏览器里派生的密钥加密 |
| 短评、回复、弹幕、片单 | 明文 |

## 关键设计

### 作品资料

豆瓣为主，TMDB 补剧照、分集和外文资料（界面署名），Wikidata 补片名、别名和外部 ID 对照，IMDb 只记 ID。短剧单独一个来源：红果短剧官网公开给搜索引擎的页面。豆瓣和这几个来源都没有的作品，作品库里就没有；用户照样能播，进度走加密历史。详见 [作品资料](metadata.md)、[短剧](short-drama.md)。

### 把资源站的结果对应到作品

浏览器调用 `POST /api/media/resolve`，只发片名、年份、类型和豆瓣 ID，不发任何源信息。服务器的查找顺序：

1. 豆瓣 ID 精确匹配（空值和 `"0"` 不算）。
2. 规范化后的片名查别名表，再按类型（只分"电影"和"分集的"两类）和年份（允许差 1 年）过滤。
3. 剩一部就是它；剩多部时最多返回 6 个候选，让用户选，选择结果记在本机。
4. 都对不上的，走加密历史。

这个接口只匹配、不收录：资源站的搜索结果里不相干的片子很多。都对不上但源给了豆瓣 ID 的，等用户真的开始播放了，播放页再调 `POST /api/media/discover` 把它收进作品库，后台去豆瓣确认并抓资料。

### 查源和播放

订阅里的所有源同时查询，哪个先返回就先显示；查询经服务器转发，视频由浏览器直接加载。资源站返回的数据一律当作不可信内容：文字用 `textContent` 显示，请求不带本站的 Cookie 和 Referer。只有 Safari 用系统自带的 HLS 播放，其他浏览器一律用 hls.js。详见 [播放源与播放器](playback.md)。

### 进度和加密历史

- 作品库里有的作品，进度按"作品 ID + 季 + 集"明文记录，电影固定为第 1 季第 1 集。不需要先建分集，没有分集资料的作品也能记。
- 作品库里没有的，整条记录（片名、源的 `key`、`vod_id`、线路、集名、进度）在浏览器里用 AES-GCM 加密后上传。记录 ID 是 `HMAC(密钥, 规范化片名|年份|类型)`：两台设备算得出同一个 ID，服务器却没法拿片名库反推。每个用户最多 2000 条，每条不超过 1 KB。
- 浏览器会定期拿加密记录去匹配作品库，匹配上以后转成明文记录，删掉加密的那条。
- 当初用的源失效时，到其他源里找同名、同类型、同年份的同一部自动换过去；有一边没写年份的只列出来让用户确认。

服务器仍能看到：每个用户有多少条加密记录、每条什么时候更新。网页版的端到端加密，前提是服务器下发的前端代码可信。

### 登录即同步

设备密钥和订阅地址合成一个"钥匙圈"，用登录密码在浏览器里派生的密钥加密后存到服务器，登录时解开，换设备不用扫码配对。取舍：服务器不保存密码，但登录时会短暂收到密码，理论上能派生出密钥。详见 [账号](accounts.md#登录即同步)。

### 广告跳过

服务器把结论列表（确认是广告的、确认不是的）下发给所有人，浏览器在本地比对，服务器不知道谁在播什么；只有投票要上传。

- 确认票 ≥ 5 且占比 ≥ 80% 算广告，自动跳过；否认票 ≥ 3 且多于确认票算不是广告，不再询问；其余当作未知，结构上高度疑似时询问用户。
- 播到广告开头时直接跳到结尾，不改写播放清单：iPhone 的系统播放器不能改写清单，按时间跳在所有浏览器上都能用。
- 不做人工裁定：管理员看不到画面，没有依据判断；自动跳过后用户可以"撤销 → 这段不是广告"投否认票。

### 数据库

只留**别处推不出来、又确实有人读**的数据：能算出来的现算，只写不读的不存。链路越短出错越少。详见 [数据库](database.md)。

### 后台任务

一部作品的采集拆成豆瓣、补充资料、AI 描述、向量四个任务，各自保存、各自重试，一步失败不连累别的步骤。豆瓣任务单独一条通道，豆瓣暂停时不取任务，被限流的失败不计次数。重试间隔从 1 分钟到 1 天逐次加长，共 6 次，之后冷却 14 天。详见 [作品资料](metadata.md)。

### 界面

一套页面适配手机、平板、电脑，同一个 `<nav>` 有三种形态（底部、左侧、顶部）。页面跳转用普通跳转，配合浏览器预渲染、页面过渡动画和返回缓存；HTMX 只用于局部更新。前端是原生 ES 模块，不需要构建。

## 决定记录

| 问题 | 决定 | 原因 |
| --- | --- | --- |
| 资源站的元数据是否用来兜底 | 不用 | 作品库不从资源站生成 |
| 字段从哪个来源取 | 豆瓣给的值总是写入，TMDB 只补空着的字段 | 写字段的来源只有两个，不需要一张表来仲裁。代价：豆瓣没给、TMDB 先补上的字段，TMDB 之后改了不会跟着更新 |
| IMDb | 只记 ID，不取评分 | 没有免费接口 |
| 不登录能看什么 | 作品详情、相似推荐、短评、发现、搜索、片单、公开主页、月度报告；个人页面和搜索结果 noindex | 2026-11-16：利于搜索引擎收录 |
| 源配置怎么跨设备 | 登录即同步，不做扫码配对 | 2026-11-16：扫码太麻烦 |
| 播放源的查询 | 由服务器转发，视频不转发 | 2026-11-17：资源站大多没有跨域许可 |
| TVBox 配置 | 只导入苹果 CMS 站点；加密配置和多仓配置暂不支持 | 2026-11-20：爬虫站点等于在本站执行第三方代码 |
| 注册 | 只填邮箱，随机密码发到邮箱 | 能收到密码就证明邮箱是本人的，省掉激活步骤 |
| 人机校验 | 工作量证明 | 不用第三方验证码，用户通常感觉不到 |
| 通知 | 点赞、回复、关注之外，还有反馈被回复、内容被管理员删除（附原因）、片单审核结果；不发邮件通知 | 反馈没有回音，用户就不会再反馈；删内容要告诉作者原因 |
| 拉新 | 作品、短评、片单、月度报告可以生成分享图片 | 通过用户已有的社交圈带来新用户，代替站内社交 |
| 片单 | 投稿审核后公开；已发布的修改也要审核，期间公开页显示旧版 | 2026-11-20：既要审核，又不能让公开页因为修改而消失 |
| 图片 | 站内签名代理，代理过的图片备份到 Telegram 频道 | 原图失效、防盗链变严时图片也还在 |
| 豆瓣被限流 | 电影详情、剧集详情、其余接口各自放慢、各自暂停：连续被限流停 10 分钟，IP 被标记（`subject_ip_rate_limit`）停 2~12 小时；可选出站代理 `DOUBAN_PROXY` | 先慢下来。2026-11-25：豆瓣分接口限流，电影详情被标记时剧集详情照常；原来每 10 分钟去试一次，让标记一直解不开 |
| 浏览器插件 | 用户装插件后，豆瓣标记在他自己的浏览器里同步；插件空闲时替服务器取作品详情（不带 Cookie、7 秒以上一次、每天最多 300 部、被拒绝就停），交回的资料服务器检查后才写入。压缩包分发，不上架应用商店；服务器原来的同步和采集保留给没装插件的用户（见 [浏览器插件](extension.md)） | 2026-11-25：服务器单一出口被豆瓣限流，同步不及时。这推翻了原来"不用志愿者节点"的决定：分到用户浏览器请求，本质就是这个；商店政策不允许替开发者采集，所以不上架 |
| 资料多久同步一次 | 连载中的每天，近两年上映的每周，其余只同步一次；近期电影这一周从列表里拿到过评分的放宽到 30 天 | 作品库越大，无差别重抓越浪费；近期电影重抓主要就是为了评分 |
| 热搜怎么存 | 每天每个词一行，内存累加、每分钟批量写入；只存次数，不存用户和 IP | 行数只和每天不同的词有多少有关，用户多了也不会膨胀 |
| 热门榜 | 豆瓣热门、TMDB 一周趋势、本站最近 7 天的观看人数按名次加权综合 | 补海外新片，并反映本站用户真正在看的 |
| 短剧 | 红果官网的公开页面；本地全量抓取一次，线上只做增量 | 2026-11-18：红果站内搜索要过风控签名，做不到只收用户查的 |
| 响应压缩 | 自己写的中间件，响应生成完再压缩 | 第三方库每个请求占一个约 1 MB 的压缩器，200 并发时内存 400 MB，现在约 120 MB |
| 个人数据 | 可以自助导出全部数据和注销账号 | 《个人信息保护法》第 45、47 条 |
| 数据库备份 | 由部署环境负责，不在本项目里 | — |
| 收费、App、律师咨询 | 目前都不考虑 | — |
