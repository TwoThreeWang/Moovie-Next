# 作品资料：采集与榜单

作品资料来自豆瓣、NeoDB、TMDB、Wikidata；AI 写语义描述并算向量，用于相似推荐。

豆瓣的请求很少（被限流时一小时只有几十次），所以建档不等豆瓣：作品一收进来，先用豆瓣列表里带的片名、年份、海报、评分，加上 Wikidata、NeoDB、TMDB 建好档、正常展示；豆瓣详情只为豆瓣独有、还会变的资料去读，按需补齐。

## 采集流程

### 一部作品的几步

```
收录（豆瓣列表的片名、年份、海报、评分）
 ├─ 建档 media.enrich：Wikidata → NeoDB → TMDB ─→ AI 描述 media.semantic ─→ 向量 media.embed
 └─ 豆瓣详情 media.refresh（按需，排在后面）─→ 成功后再排一次 media.enrich，按豆瓣的资料补齐
```

每一步是一个单独的任务，成功了马上保存、再排下一步；失败了只重试这一步，不会让前面的步骤重来。

1. **建档**（`media.enrich`，默认通道，不用豆瓣）：
   - **Wikidata** 按豆瓣 ID（`P4529`）精确对应，给出 Wikidata、IMDb、TMDB 编号，中文片名（简体优先）和各语言片名（成为别名）。只凭豆瓣 ID 收进来的作品（老链接）靠它拿到片名。
   - **NeoDB**（`NEODB_URL`，默认 `https://neodb.social`）：用片名搜索（`/api/catalog/search`），只认带着同一个豆瓣链接的条目；电影也可以是同一个 IMDb 编号、没挂别的豆瓣链接的条目（剧集的 IMDb 编号是整部剧的，分不出第几季，只认豆瓣链接）。取简体中文片名、其余中文片名（成为别名）、中文简介、类型（英文的换成豆瓣的中文类型名，认不出的不取）、导演、主演，以及 IMDb 编号和这一季的 TMDB 编号（第一季优先用带季号的链接，也可以用唯一的整剧链接；有多个候选就留空）。**评分是 NeoDB 自己用户打的分，不取。** 不用 `/api/catalog/fetch`：它碰上没收录的条目会替我们去抓豆瓣。NeoDB 是志愿者维护的站点，每 2 秒最多一次；豆瓣详情同步过以后不再去问它；它出错只记日志，不让这一步重试。
   - **TMDB**：剧照、分集、连载状态、TMDB 评分，其余空着的字段也用它的。找条目的顺序：已存的编号 → 用 IMDb 编号反查 → 片名加年份搜索。按片名搜索时选唯一的同名结果，再核对已知年份和季。找到后补空着的片名和年份，剧集用对应季的首播年。只有豆瓣 ID、别处也还没给出片名时不搜。
   - 片名可能是这一步才有的，屏蔽词在这一步就查，命中的隐藏，不等豆瓣。
2. **豆瓣详情**（`media.refresh`，豆瓣通道）：片名、年份、简介、类型、地区、导演、主演、评分、海报、又名。已知是电影还是剧集时先试对应的接口，猜对了只发一次请求。豆瓣确认没有这个条目（两个接口都是 404）就记成 `not_found` 并隐藏，以后从任何入口送来都不再请求。请求之前再确认一次还要不要去（见[巡检挑哪些作品](#巡检挑哪些作品)）：任务可能排了很久，期间插件交来了资料、或者已经不需要了，就不去请求；管理员手动刷新不管这些。成功后按豆瓣的资料再补一轮建档。
3. **AI 写语义描述**（`media.semantic`）：把资料发给大模型（OpenAI 格式的 `/chat/completions`），写成一段 200 字以内、语义密度很高的描述，保存到 `semantic_text`。提示词和资料格式固定（`internal/ingest/prompt.go`、`media.SemanticInput`），导入的历史描述也是按这个格式写的，不必重新生成。`semantic_hash` 记着写描述时所用资料的哈希：资料没变就不再调用 AI。豆瓣详情同步以后才写；豆瓣一直没补上的，建档 3 天后（`media.PartialSemanticAfter`）按现有的资料写，豆瓣补上以后资料变了会再写一遍。
4. **算向量**（`media.embed`）：用语义描述算 768 维向量（OpenAI 格式的 `/embeddings`，默认模型 `quentinz/bge-base-zh-v1.5`）。描述改写了，旧向量随之清空重算。

描述和向量分开保存：AI 成功、向量失败时，描述留着，重试向量不会再调用一次 AI。没配 AI 时不写描述，新作品也就没有向量，相似推荐改按类型重合度。

### 几个来源写同一个字段

每轮先用 Wikidata 找外部编号、别名和查找用的片名，再用 NeoDB 的中文资料优先补齐，TMDB 补这一轮余下的空字段。写入时，片名、简介、海报等共用字段只填库里仍为空的值；如果 NeoDB 查询失败而 TMDB 已填上简介，之后按同一规则保留现有简介。豆瓣列表提供的基本资料也按空值补齐，列表评分直接更新。

服务端豆瓣详情和通过校验的插件提交使用同一规则：有值就覆盖，缺失值保留。季号只在片名或原名明确包含季号时更新。TMDB 负责刷新集数、剧照、分集、连载状态和 TMDB 评分。

### 什么时候采集

| 入口 | 什么情况下 | 豆瓣详情的优先级（越大越先做） |
| --- | --- | --- |
| 打开详情页 | 还没建档的，马上排建档（优先级 20）。**登录用户**打开、豆瓣还没同步过的，豆瓣详情也提到最前面，被限流推迟到以后的也提前到现在。没登录的访客（包括爬虫）打开不会去请求豆瓣 | 20 |
| 管理员 | 按豆瓣 ID 添加作品，或者点"刷新"。不管冷却期，整条重跑 | 10 |
| 热门榜单 | 每 6 小时刷新一次，榜单里新出现的作品 | 5 |
| 老站链接 | 库里没有的豆瓣 ID 先按低优先级建档，豆瓣详情等登录用户打开或巡检 | — |
| 站内搜索 | 登录后，作品库里不到 3 个结果时去豆瓣查联想（同一个词一天一次），查到的新作品 | 5 |
| 本地播放 | 从搜索页"我的源"点进作品库里没有的作品、播放源带了豆瓣 ID，开始播放后（`POST /api/media/discover`，每个账号每分钟最多 20 个）。搜索时的片名匹配只读，不收录 | 5 |
| 导入豆瓣标记 | 用户点"同步"是完整同步（优先级 5）；每天自动的那次是增量同步（-2）：先看用户的 RSS，上一次同步之后没有新的看过或想看就一页都不读，只有一种有新动态就只读那一种；RSS 读不到、或者最早的一条也比上一次同步晚（RSS 只有最近十来条）时照常翻标记列表，读到整页都已导入就停。换绑或解绑豆瓣账号会清掉同步记录，下一次增量同步照常翻标记列表。上一次同步有标记没能收进作品库（数据库出错之类），或者这次是中途出错后的重试，就不看 RSS、也不读到整页已导入就停，而是完整地读一遍：没导入的那几条可能在列表靠后、又早于上一次同步，增量的两种办法都会把它们当成处理过了。直到有一次同步没有失败才恢复增量。不合法的条目 ID 收不进来，不算失败 | — |
| 导入带来的新作品 | 列表里已经有片名、海报和评分，晚点补全不影响使用 | 0 |
| 每小时巡检 | 漏掉的都补上（见下） | -1 / -2 |

榜单、搜索和用户导入收录的新作品同时排建档和豆瓣详情；建档走默认通道，不占豆瓣的额度。

### 失败了怎么办

- 重试间隔逐次加长：1 分钟、10 分钟、1 小时、6 小时、1 天，共 6 次（约 31 小时）。用完标记为失败。
- **冷却期**：失败记录保留 14 天，这期间这部作品的这一步不会再被任何入口排进来（管理员手动刷新除外），一个一直出错的作品不会被反复送去请求对方。成功一次就清掉失败记录。
- Wikidata 或 TMDB 出错只算建档失败，豆瓣不会再被请求；重试用完时照样往下写描述，过了冷却期由巡检再补一次。豆瓣同步完时建档正处在冷却期的，直接往下写描述。
- 豆瓣详情一直失败不影响建档：作品照样能展示、能搜到，只是少了豆瓣独有的资料。
- 豆瓣限流：任务放回队列稍后再做，不算失败。一般是一分钟后；豆瓣的某个接口在暂停时（连续被限流停 10 分钟，IP 被标记停几个小时，见[豆瓣请求节奏](#豆瓣请求节奏)），推迟到这个接口恢复的时候。只停了电影详情时，剧集的刷新、标记同步和榜单照常做；电影详情、剧集详情和其余接口都停了，整条豆瓣通道才先不取任务，任务原样等着，但有人在等的（优先级 10 以上）照样取出来去读详情网页。榜单四类全失败时也认得出限流，同样推迟。从第一次被推迟算起超过 3 天的任务再被限流就按普通失败算，免得某个条目一直被拒绝、永远在队列里转。

### 巡检挑哪些作品

- 建档：还没补过的（不管豆瓣同步过没有），和豆瓣同步之后还没按新资料再补一轮的，新收录的在前，一次最多 500 部。
- 连载剧：每小时挑最多 100 个已关联 TMDB、尚未确认完结、一天没刷新或从未查过的季，按最久未刷新优先，只查 TMDB。以同一季的资料更新集数、分集和播出状态，确认完结的季退出巡检。确认不了对应季时，隔一周再查。
- 豆瓣详情（`media.Store.Stale`）：从没同步成功过的；近两年上映的每周最多一次（评分和简介还在变），这一周已经从热门榜或用户的标记列表里拿到过评分的放宽到 30 天。连载剧的集数和播出状态由 TMDB 更新，不为它们去读豆瓣；更早的作品同步一次就够了，后台仍然可以手动刷新。
- 热门榜、用户的标记列表里本来就带着评分、年份、海报：已有的作品顺手更新，评分直接写，年份和海报只补空着的（列表里的海报可能比详情的小一档），不为此再请求详情。
- 详情接口被限流、或者对个别条目返回 403 时，有人在等的作品（登录用户开着作品页、管理员手动刷新）改打开详情网页（`movie.douban.com/subject/<id>/`）读资料。网页有自己的节奏（基准 5 秒一次），详情接口暂停时它照样能用；后台批量的任务不走这条路，免得它也很快被限流。网页说没有这个条目时不算数。只带豆瓣 ID、还没有片名的作品，电影详情被限流时可接着试剧集详情。已有片名的电影会等电影接口恢复。
- 语义描述：资料够了（有片名和简介或原名）、豆瓣同步过（或者建档 3 天还没等到豆瓣）、还没有语义描述的。正在建档的先不挑，免得 AI 按不全的资料写一遍、补完又写一遍。
- 向量：有描述、没向量的。
- 正在排队、运行或处在冷却期的作品都不挑，一批一直失败的作品不会每次都排在最前面、把别的挤掉。

### 豆瓣 ID 的过滤

- 格式：7–9 位数字，不以 0 开头（豆瓣的条目编号从 100 万开始）。不合格式的不收录，也就不会拿去请求。
- 豆瓣确认没有的 ID（比如图书、音乐的条目）永久记住，不再请求。
- 一直出错的 ID：6 次重试用完后冷却 14 天。

### 执行通道

- 豆瓣通道：3 个执行位，请求快慢由各接口自己的节奏控制（见[豆瓣请求节奏](#豆瓣请求节奏)）。读豆瓣详情、刷新榜单、同步用户标记都走这里；用户同步最多占两个位置。
- AI 通道：2 个执行位。写一段描述要十几秒到一分钟，不让它堵住别的任务。
- 红果通道：2 个执行位，共用每秒一次的限速，只做短剧的任务（见"短剧"）。
- 默认通道（`WORKER_CONCURRENCY`，默认 2）：建档（Wikidata / NeoDB / TMDB）、算向量、巡检、清理。

后台概览显示还有多少作品在等、最早的等了多久、照现在的速度大约多久做完。完成的任务记录保留 3 天。重启不会把周期任务（榜单、巡检、每日同步）立刻再跑一遍。

## 豆瓣请求节奏

豆瓣分接口限流：电影详情（`/rexxar/api/v2/movie/<id>`）被限流的时候，同一个 IP 打开剧集详情（`/tv/<id>`）、标记列表照样正常。所以请求分成四条节奏，各自放慢、各自暂停：

| 节奏 | 接口 |
| --- | --- |
| 电影详情 | `/rexxar/api/v2/movie/<id>` |
| 剧集详情 | `/rexxar/api/v2/tv/<id>` |
| 其余接口 | 标记列表、榜单、搜索联想、RSS |
| 详情网页 | `movie.douban.com/subject/<id>/`（详情接口的兜底） |

每条的基准间隔都是 5 秒（`doubanInterval`），每次再随机多等 0~50%，平均每 40 次请求再歇 5~15 个基准间隔，平均下来大约 7.5 秒一次：分毫不差的固定间隔一看就是程序。抖动只往上加，两次请求之间不会短于当前间隔。以前按 0.8 秒请求，2026-11-25 批量刷新时四分钟请求了将近两百次，豆瓣就标记了这个 IP。

哪条节奏被限流，就只停哪条：

- 返回 403 / 418 / 429、错误名里带 `rate_limit`、被转到验证页（`sec.douban.com`、`/misc/sorry`）、或者该是数据的地方返回了网页，都算被限流：间隔翻倍，最多 1 分钟；连续 3 次就暂停 10 分钟；之后每成功一次，间隔缩回一点。
- 返回 `subject_ip_rate_limit`（code 1309，"您所在的网络存在异常，请登录后重试"）说明豆瓣标记了这个 IP。这时请求头、Cookie 换成什么样都一样被拒绝，再去试只会让标记一直解不开，所以不等连续几次，立刻暂停 2 小时；恢复后的第一个请求又被标记就翻倍，最多 12 小时；成功一次后回到 2 小时。
- 暂停期间的请求直接失败，页面不会卡住；任务推迟到这条节奏恢复的时候再做，不算失败。排着队等的请求醒来时发现已经暂停了，也不再发出去。
- 暂停记在进程的内存里，重启就没了。所以 worker 启动时，把重启前因为限流推迟到以后的任务提前到现在（`jobs.Queue.ResumePostponed`）：换了代理重启后不用干等几个小时，豆瓣还在限流的话会重新推迟。
- 用电影接口查剧集时豆瓣会跳到剧集接口。不跟着跳，改按剧集接口自己的节奏去查：剧集接口暂停着就不发；那边被限流也只停剧集接口。
- 每个请求在节奏里占一个时段。搜索页只等 4 秒，等不到轮到自己就直接不查，不占时段；等到一半取消的，把时段还回去，不把后面的请求往后推。

错误信息里带着请求的接口和豆瓣回答的错误名、错误码、说明，比如 `豆瓣 /rexxar/api/v2/movie/1889152 返回 HTTP 400 subject_ip_rate_limit（code 1309，您所在的网络存在异常，请登录后重试。）；豆瓣电影详情暂停到 23:40`。需要时可以用 `DOUBAN_PROXY`（http / https / socks5）让豆瓣的接口请求走指定的出站代理。

配了 `DOUBAN_PROXY` 时，程序把它当成会轮换出口的代理（比如 mihomo 的轮询负载均衡）：

- 不复用连接，每个请求新开一条。代理按连接换节点，复用连接的话所有请求一直从同一个出口出去，也全压在这一个 IP 上。
- 一个出口被拒绝（403、429、验证页）、被标记（`subject_ip_rate_limit`）或者连不上，换一个出口再试，一个请求最多试 3 个出口（`exitTries`），每次都按节奏排队，不会因此请求得更快。404、跳到另一个接口、解析失败和出口无关，不换。
- 3 个出口都不行才记一次：被标记的先只放慢，接连 3 次这样（中间没有成功）才按上面的办法停 2~12 小时；其余的照上面算。最后一个出口连不上时按前面豆瓣的回答算。
- 2026-11-26 实测一个机场订阅：同一时刻四个节点里，一个能打开电影详情，一个 403 `need_permission`，一个 `subject_ip_rate_limit`，一个 TLS 连不上。以前第一个出口被标记就整条停 2 小时，好的出口也用不上。
- 出口不轮换的代理（WARP、只连一台服务器的 VPN）也按这样处理：被标记时一个请求会多试两次，接连 3 次才停，比直连多发 8 个请求。

请求头扮成普通浏览器：手机版接口（`m.douban.com`）用 iPhone Safari 的 UA，网页版（`movie.douban.com`、`www.douban.com`）用电脑上 Chrome 的 UA（`DOUBAN_MOBILE_UA`、`DOUBAN_DESKTOP_UA`，留空用 `providers.DefaultMobileUA`、`DefaultDesktopUA`），网页版的 `/j/` 接口还带 `X-Requested-With: XMLHttpRequest`，详情接口的 Referer 是条目自己的页面（`m.douban.com/movie/subject/<id>/`）；都带中文的 `Accept-Language`。

所有豆瓣请求带同一串 Cookie（`DOUBAN_COOKIE`）：用浏览器从服务器的出口打开豆瓣、过了验证后拿到的那一整串（`bid`、`ll`、统计 Cookie 和过验证后的 `dbsawcv1`），不要带登录 Cookie `dbcl2`。同一个 IP 几分钟里冒出几十个不同的 `bid` 本身就是机器的特征，所以不再每次随机生成。`dbsawcv1` 多半和过验证时的出口 IP、有效期绑在一起，换了出口或过期后又被转到验证页时，重新过一次验证换掉这串 Cookie。写进 `.env` 时用单引号包住，里面的 `$`、`"` 才不会被转义。

想用买的 Clash 订阅：网站本身不认识 Shadowsocks、VMess、Trojan 这些协议，所以另外跑一个 mihomo（Clash.Meta 内核）容器，把订阅变成一个 HTTP / SOCKS5 代理，再把 `DOUBAN_PROXY` 指过去。仓库里不带 mihomo 的配置，需要自己部署，建议：

- 单独的容器、单独的 Docker 网络：不用 host 网络、不建 TUN 网卡、不要额外权限，不向宿主机开放端口，宿主机的网络不受影响。
- mihomo 放在 `mihomo_default` 网络里（`docker-compose.yml` 已让网站和 worker 加入这个网络），在 `.env` 里填 `DOUBAN_PROXY=http://mihomo:7890`；mihomo 只接受 Docker 内网的连接，也可以再加用户名密码。
- 节点放在一个负载均衡组（`type: load-balance`）里，写明 `strategy: round-robin`：默认的 `consistent-hashing` 按域名分节点，豆瓣的请求会一直走同一个节点。程序每个请求新开一条连接，轮询才能让连续的请求从不同的节点出去。健康检查用通用地址，不额外打扰豆瓣。填了订阅链接的配置文件不要提交到仓库。
- 检查出口会不会换：`docker run --rm --network container:moovie-worker curlimages/curl:8.11.1 -s -x http://mihomo:7890 https://api.ipify.org` 连跑几次，每次的 IP 应该不一样。

## 热门榜

首页和发现页的电影、剧集、综艺、动漫四个榜，每 6 小时重新生成一次，结果整批写进 `chart_items`。每一类综合三个来源，每部作品的分数 = Σ 权重 ÷ (20 + 名次)：

| 来源 | 权重 | 说明 |
| --- | --- | --- |
| 豆瓣热门 | 0.5 | 先用网页版的热门榜（`movie.douban.com/j/search_subjects`，电影、剧集取"热门"，综艺取"综艺"，动漫取"日本动画"）；取不到或是空的再用手机版接口：电影取热门电影，剧集取国产剧和美剧交替合并，综艺、动漫取各自的榜单。最贴近国内观众，作为主体 |
| TMDB 一周趋势 | 0.2 | 只分电影和剧集两个榜，剧集趋势里的作品按作品库里的类型分到剧集、综艺、动漫。只算作品库里已有的（按 `tmdb_id` 对应，一部剧取最新一季），不会因此去请求豆瓣 |
| 本站热播 | 0.3 | 最近 7 天看的人数（`playback_positions`，同一个人看多少集都只算一次）。最近 7 天看过东西的人少于 20 时不计入，免得两三个人就能把一部片子顶上榜 |

- 只用名次，不用各家的评分或热度值：那些数没法放在一起比。"20 + 名次"让前几名之间拉开差距，又不会让单一来源的第一名压过同时出现在几个来源里的作品。
- 每个榜取前 50 部。某一类的豆瓣榜取不到时这一类保持原样；TMDB 取不到就这次不算它。
- IMDb 没有免费的热门接口，只用来对应作品，不作为热度来源。

## 热搜榜

`/trends`，有"今天"（最近 24 小时）和"本周"（最近 7 天）两个榜；搜索页显示本周前 10 名。

- **怎么记**：用户在搜索页停下来 1.5 秒、作品库里有结果，浏览器才上报一次（`POST /api/search-log`，每个 IP 每分钟最多 30 次）。同一个人（登录用户按账号，游客按 IP）10 分钟内同一个词只算一次。
- **怎么存**：`search_counts` 每天每个词一行（日期、规范化的词、显示用的写法、次数），不存是谁搜的，也不保存每一次搜索，所以行数取决于每天有多少个不同的词，和搜索次数无关。计数先在内存里累加，每分钟用一条语句批量写入（已有的词加上新的次数）；服务停下时再写一次。保留 31 天（后台概览要画 30 天的搜索趋势）。
- **怎么排**：同一个词的不同写法合并计数，显示最近一天里的写法。库里只有按天的计数，"最近 24 小时"用滑动窗口近似：今天的全部 + 昨天的数 ×（今天还没过去的比例），"本周"同理。至少 2 次才上榜，命中屏蔽词的不上榜。和上一个同样长度的时间段比：以前没有的标"新上榜"，次数达到上次的 1.5 倍以上标"上升"。热度条按榜首的比例画。
