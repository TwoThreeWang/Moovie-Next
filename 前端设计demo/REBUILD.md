# 新版 Moovie 重构方案（讨论整理）

整理日期：2026-11-15。本文汇总了围绕"把 Moovie 重做成 SaaS"的全部讨论，分为已定的决定、设计方案和还没定的问题。界面部分的设计见 [DESIGN.md](DESIGN.md)，原型见 [README.md](README.md)。

> 文中的合规判断是按常见法律逻辑做的分析，不是法律意见。上线收费前，请找做知识产权的律师过一遍。

---

## 1. 产品定位

| 项 | 决定 |
| --- | --- |
| 形态 | SaaS，只有登录用户可用；未登录只显示产品介绍页 |
| 平台做什么 | 统一采集和整理影视**元数据**；提供观影管理、发现、社区功能 |
| 平台不做什么 | 不提供、不推荐、不存储任何播放源 |
| 播放源 | 完全由用户自己填写（订阅地址方式） |
| 收费 | 基础功能免费；部分功能收费，例如同步豆瓣的想看和已看 |

一句话：**平台是"元数据 + 观影管理"服务，外加一个中立的播放器；内容源由用户自带。**

---

## 2. 合规红线

这几条决定了产品的性质，重构时任何功能都不能越过。

1. **服务器上没有任何会访问资源站的代码。** 搜源、取播放地址、解析，全部在用户的浏览器里完成。
2. **视频流不经过服务器。** 不代理、不改写、不缓存 m3u8 和分片。
3. **不提供源。** 没有默认源、源推荐、源市场，也没有用户之间共享源的功能。
4. **服务器上没有明文的源信息。** 源配置、"上次用的哪个源"、资源站的 `vod_id`，要么只存在用户本地，要么加密后服务器解不开。
5. **作品库不从资源站生成。** 元数据只来自豆瓣、TMDB、IMDb、Wikidata 这类来源。
6. **收费功能和播放无关。** 国内司法实践里"营利目的"包括会员费这类间接获利，所以卖点要落在"管理和发现"上。
7. **宣传和界面不暗示"免费看片"。** 一句这样的文案就足以证明知情。
8. **保留通知—删除机制**，收到投诉及时处理。

### 做到以后还剩什么风险

结构上接近 Kodi、Stremio 的模式，风险从"高"降到"中"，降不到零。剩下的主要是：

- 产品整体观感：输入格式是苹果 CMS 接口、带去广告功能，都说明你知道源是什么。
- 用户在你的界面里完成"找片—选集—播放"全过程，国内法院可能据此认定实质替代。
- 元数据来源的商用授权（见第 4 节）。

### 讨论过但放弃的方案

| 方案 | 放弃原因 |
| --- | --- |
| 平台统一采集并存储资源（现在的系统） | 平台自己在做盗版聚合 |
| 后端按需采集、流式返回、不存储 | 服务器仍在访问资源站并发出播放链接；"不存储"只是少留证据。另有 SSRF 和服务器 IP 被封的问题 |
| 用资源站的元数据兜底补全作品库 | 会让作品库和盗版站目录挂钩，而且需要服务器读资源站（**你最初的设想里有这一条，是否放弃还需你确认，见第 10 节**） |

## 3. 整体架构

```
┌──────────────── 浏览器（用户设备） ────────────────┐
│  订阅管理 ─ 查源 ─ 解析 ─ 匹配作品 ─ 播放 ─ 去广告   │
│  本地存储（IndexedDB）：订阅缓存、查源结果、         │
│  上次用的源、主密钥、未匹配历史的明文副本            │
└───────┬───────────────────────────┬───────────────┘
        │ 只有元数据和用户数据         │ 直连，服务器不参与
        ▼                           ▼
┌──── Moovie 服务器 ────┐      ┌── 用户自己填的资源站 ──┐
│ 作品元数据、账号、      │      │ 搜索接口、m3u8、分片    │
│ 想看/看过、播放进度、   │      └───────────────────────┘
│ 弹幕/短评/片单、        │
│ 广告指纹、加密历史      │
└───────────────────────┘
```

### 服务器上关于用户的全部数据

| 数据 | 形式 |
| --- | --- |
| 账号、设置、想看和看过 | 明文 |
| 播放进度（有元数据的作品） | 明文，只有作品 ID、集数、进度 |
| 播放进度（没有元数据的作品） | 密文，服务器解不开 |
| 弹幕、短评、片单 | 明文，按作品 ID 和集数 |

## 4. 元数据

### 来源和授权

| 来源 | 商用情况 | 建议用途 |
| --- | --- | --- |
| TMDB | 商用需要和 TMDB 签协议；界面必须署名 | 作品库骨架 |
| Wikidata | CC0，可随意商用 | 片名、别名、外部 ID 对照 |
| 豆瓣 | 没有开放 API，只能爬；商业产品大规模抓取有被判不正当竞争的先例 | 用户自己账号的同步；少量补充（中文简介、评分） |
| IMDb | 官方数据集只限非商业用途；商用要付费授权 | 有收费功能时不能直接用 |

你设想的优先级是"豆瓣 > IMDb/TMDB"，数据质量上没问题，但合规上正好相反。**这一条还没定，见第 10 节。**

海报和剧照本身也有版权，图片来源要跟着元数据来源走。

### 作品匹配接口

浏览器把资源站结果对应到作品 ID 时调用，只发送片名这类信息，不发送任何源信息：

```http
POST /api/media/resolve
[{ "douban_id": "36154853", "title": "雾港", "year": 2026, "type": "tv" }]
```

服务器的查找顺序：

1. 豆瓣 ID 精确匹配（先排除空值和 `"0"`）。
2. "片名 + 年份 + 类型"匹配，并查别名表。
3. 匹配到多部时返回候选列表，让用户选；选择结果记在用户本地。
4. 匹配不到的，走加密历史（见第 7.2 节）。

## 5. 前端查源引擎

### 5.1 订阅

用户把源列表放在自己控制的地址上（私有 Gist、网盘等），每台设备只填这一个地址。

```json
{ "version": 1, "sources": [
  { "key": "lz", "name": "量子", "api": "https://…/api.php/provide/vod/", "type": "cms-json" }
]}
```

- 每个源要有稳定的 `key`。没填的，用规范化后的接口地址算哈希代替；代价是接口地址一变就被当成新源。
- App 启动或页面重新获得焦点时重新拉取订阅，支持的话带 `If-None-Match`。
- 新旧列表按 `key` 对比：
  - 被删掉的源：清掉指向它的本地缓存。
  - `key` 没变、接口地址变了：缓存保留，直接用新地址。
  - 新增的源：不用处理。

### 5.2 查询流程

1. 所有源同时请求，哪个先返回就先显示哪个。
2. 每个源用 `AbortController` 设 3–4 秒超时。
3. 每个源只请求第一页（`pg=1`）。
4. 同一个源里，先用豆瓣 ID 对应作品，没有再用片名。
5. 结果缓存在 IndexedDB（作品 → 各源结果），先显示缓存，再后台刷新。
6. 详情页一显示就开始查源，用户读完简介时结果通常已经回来。
7. 在本地记录每个源的成功率和加载速度，下次优先用好的源。

### 5.3 浏览器的两条限制

| 限制 | 处理 |
| --- | --- |
| 跨域（CORS） | 按你的判断，资源站一般不限制，**先不考虑**。遇到被拦的源，提示用户换源 |
| HTTPS 页面不能请求 HTTP 地址 | 接口是 HTTP：请求前就判断，提示"该源不支持 HTTPS"。播放地址是 HTTP：先改成 `https://` 试一次，失败就在这条线路上提示，并自动切到下一条 |

以后如果用不了的源太多，可选的补救方式都不经过你的服务器：浏览器扩展、App 外壳（Capacitor、Tauri）、用户自建代理。

### 5.4 安全

1. **资源站返回的数据一律当作不可信内容。**
   - 文字用 `textContent` 显示；简介先去掉所有标签。不用 `innerHTML`。
   - 播放地址和图片地址只接受 `https:` 开头的。
2. **CSP** 要放开到任意 HTTPS 地址：`connect-src https:`，`media-src` 和 `img-src` 允许 `https:` 和 `blob:`。这会让 CSP 变弱，所以第 1 条不能省。
3. **请求不带自己网站的信息：** `credentials: 'omit'`，`referrerPolicy: 'no-referrer'`。
4. **容错：** 少数源只返回 XML，用 `DOMParser` 解析；字段为空、集名不统一时跳过坏数据，不让整个源报错。

### 5.5 性能

模拟一次典型返回（20 部作品，每部 2 条线路、每条 40 集，约 112KB），在 Mac 上解析并拆分大约 0.14ms。按中端手机慢 4–6 倍估算，10 个源合计也不到 10ms。解析不需要放进 Web Worker，瓶颈在网络。

和后端查询相比，用户能感觉到的差别只有：第一次打开某部作品时，"可播放的源"大约晚 0.5–1.5 秒出现。起播速度一样。

## 6. 播放

- 视频直连用户的源。浏览器能原生播放 HLS 时不加载 hls.js。
- 进度按作品 ID 和**标准集数**记录。前端从资源站的集名（"第05集""05""EP5"）里解析出集数，再对应到作品库的集。

### 6.1 继续观看和换源

```
有"上次用的源"缓存，并且这个源还在订阅里？
 ├─ 是 → 直接请求这个源的对应集 → 从保存的进度开始播
 └─ 否，或者请求失败
      → 同时查询订阅里的所有源，找第一个对应同一部作品、并且有这一集的源
      → 从保存的进度开始播，更新本地缓存
```

- 换源时往回倒 5 秒。
- 两个源的总时长相差 5% 以上时，提示"已切换来源，进度可能有偏差"。

### 6.2 去广告

沿用现有设计（见仓库里的 `docs/M3U8广告指纹众包跳过功能交接文档.md`）：

- 表里只有"指纹 + 确认数 + 否认数"，不存源、影片、集数、时间，也不存谁投了什么票。
- 前端只分析 m3u8 文本并计算指纹，后端不代理、不改写。

需要收紧的地方：

- Gin、Nginx、限流组件的日志不记录匹配接口的请求体，也不把用户 ID 和这个接口关联起来。
- 可选：把"已确认"的指纹做成静态文件，前端本地匹配，播放时不再请求服务器。**这和现有文档的决定相反，见第 10 节。**

### 6.3 弹幕

- 用户自己发的弹幕，按作品 ID 和集数存储，问题不大。
- 从 B 站、腾讯视频等平台抓弹幕，涉及不正当竞争和平台协议，**是否保留见第 10 节。**

## 7. 云同步

### 7.1 有元数据的作品：明文同步

沿用现有 `playback_positions` 的增量同步机制（`server_version`）。

- **字段：** `user_id`、`media_id`、`media_unit_id`、`position_seconds`、`duration_seconds`、`completed`、`activity_at`、`server_version`、`deleted_at`。
- **不要的字段：** `last_source_key`、`last_vod_id`、`legacy_payload`；`title`、`poster` 可以从作品表查。
- **上报：** 暂停、切换集数、每 30 秒一次；离开页面时用 `navigator.sendBeacon` 补一次。
- **拉取：** 页面重新获得焦点时，取某个 `server_version` 之后的变化。
- **冲突：** 以 `activity_at` 较新的为准，不取较大的进度（用户可能往回拖）。

### 7.2 没有元数据的作品：加密后同步

```sql
CREATE TABLE private_history (
  user_id        bigint NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  rid            bytea  NOT NULL,   -- 32 字节，服务器不知道它代表什么
  server_version bigint NOT NULL DEFAULT nextval('private_history_seq'),
  blob           bytea,             -- 密文；为空表示已删除
  updated_at     timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (user_id, rid)
);
```

- **记录 ID：** `HMAC(密钥, 规范化片名|年份|类型)`。两台设备能算出同一个 ID；不能用普通哈希，否则服务器可以拿片名库反推。
- **密文内容：** 片名、年份、源的 `key`、`vod_id`、线路、集名、进度、时间。AES-GCM 加密，每次随机 IV，加密前补齐到固定长度（如 512 字节）。
- **冲突：** 上传带 `If-Match: <server_version>`，不一致返回 409；客户端拉取、解密、比较里面的播放时间，再决定用哪份。
- **自动迁移：** 客户端定期对这些记录调用 `/api/media/resolve`。匹配上以后写一条明文记录，并把加密记录标记为删除。
- **限制：** 每个用户最多 2000 条，每条不超过 1KB，并限制写入频率。服务器看不到内容，不限制的话会被当成网盘。

服务器仍能看到：每个用户有多少条加密记录、每条什么时候更新。

### 7.3 密钥和设备配对

- 第一次使用时，浏览器随机生成一个主密钥，存在本机 IndexedDB。加密密钥和 `rid` 用的密钥都用 HKDF 从主密钥派生。
- **不从登录密码推导**（服务器登录时能看到密码），**也不从订阅地址推导**（订阅地址常被公开分享，而且会变）。
- 配对新设备：老设备显示二维码，内容是

  ```
  https://你的域名/pair#sub=<订阅地址>&k=<主密钥>
  ```

  `#` 后面的内容不会发给服务器。扫一次码，新设备同时拿到订阅地址和密钥。电脑上可以手动粘贴。
- 密钥丢了，加密历史找不回来；可以从任意一台已配对的设备再扫一次码。

限制：网页版的端到端加密，前提是服务器下发的前端代码可信。这是所有网页端加密的通病。

### 7.4 "继续观看"怎么显示

页面由服务端渲染，服务器只能输出明文记录。加密的那部分，前端从本地 IndexedDB 的解密副本里读取，页面一加载就按时间顺序插入；服务器同步在后台进行。

## 8. 数据库：和现有系统相比

按表名和已核对过的字段判断，标"待确认"的没有逐一看过。

### 新系统不再需要

| 表 | 原用途 |
| --- | --- |
| `sites` | 平台维护的资源站列表 |
| `vod_items`、`resource_play_lines`、`resource_episodes`、`resource_episode_candidates` | 采集来的影片、线路、剧集 |
| `resource_media_links`、`resource_match_candidates`、`resource_match_audits` | 资源和作品的匹配 |

| `resource_playback_health`、`playback_results`、`playback_attempt_events`、`playback_quality_rollups` | 按源统计能否播放、加载速度 |
| `watch_histories` | 旧历史表，含 `source`、`vod_id` |

### 保留这些概念

| 类别 | 表 |
| --- | --- |
| 作品元数据 | `media`、`media_units`、`media_aliases`、`media_external_ids`、`media_field_sources`、`metadata_refresh_jobs`、`popularity_snapshots` |
| 用户 | `users`、`user_movies`、`user_follows`、`douban_sync_jobs`、`user_recommendation_snapshots`、`monthly_reports` |
| 播放进度 | `playback_positions`（去掉源字段，见 7.1） |
| 社区 | `danmakus`、`comment_likes`、`comment_replies`、`collections`、`collection_items`、`collection_relations`、`social_notifications`、`feedbacks` |
| 广告指纹 | `ad_fingerprints` |
| 过滤和合规 | `copyright_filters`、`nsfw_filters`、`content_filters`、`category_filters` |

### 新增

- `private_history`：加密历史（见 7.2）。

### 待确认

`media_source_snapshots`、`search_discovery_probes`、`legacy_media_mappings`、`history_sync_events`、`movies`、`search_logs`、`trending_keywords`：要看里面是否含资源站的数据，再决定去留。

## 9. 界面

沿用 `tvui-lab/` 里已经做好的自适应原型：

- 一套页面适配手机、平板、电脑；同一个 `<nav>` 有三种形态（底部、左侧、顶部）。
- 首页首次加载（不含图片）gzip 后约 33KB，预算是 60KB。
- 页面跳转用普通跳转，配合浏览器预渲染、页面过渡动画和返回缓存；HTMX 只用于局部更新。

新方案要补的页面和状态：

| 页面或状态 | 内容 |
| --- | --- |
| 介绍页 | 未登录用户看到的产品介绍 |
| 源设置 | 填订阅地址、查看各源状态、手动刷新 |
| 设备配对 | 显示和扫描二维码、手动粘贴 |
| 详情页的源区域 | 查源中、无可用源、源不支持 HTTPS、已切换来源 |
| 没填订阅时 | 作品页可以正常浏览和标记，播放入口引导去设置源 |
| 作品匹配 | 多个候选时让用户选是哪一部 |
| 会员 | 收费功能说明（豆瓣同步等） |

## 10. 还没定的问题

| # | 问题 | 我的建议 |
| --- | --- | --- |
| 1 | 是否彻底不用资源站的元数据兜底 | 不用；匹配不到的作品走加密历史 |
| 2 | 元数据优先级：豆瓣优先，还是 TMDB + Wikidata 做骨架 | 有收费功能的话，用 TMDB（签商用协议）+ Wikidata 做骨架 |
| 3 | IMDb 数据用不用 | 商用不能直接用官方数据集 |
| 4 | 广告指纹：每次播放查服务器，还是下发静态列表本地匹配 | 静态列表，服务器不知道谁在播 |
| 5 | 第三方平台的弹幕要不要抓 | 只保留用户自己发的 |
| 6 | 手机上用不了的源（HTTP、跨域）要不要做 App 外壳 | 先上网页版，看实际比例再定 |
| 7 | 除订阅外，要不要支持"端到端加密同步源配置" | 先只做订阅 |
| 8 | 现有用户的数据怎么迁移（历史记录里带源的字段） | 迁移时只保留能对应到作品 ID 的进度 |
| 9 | 现有的图片代理是否保留 | 取决于第 2 条定的图片来源 |
| 10 | 律师咨询 | 方案定稿后、上线收费前做一次 |

## 11. 建议的实施顺序

1. **定第 10 节的前 5 个问题**，它们决定数据库和接口长什么样。
2. **元数据服务：** 新库的作品表、采集和匹配接口。
3. **账号和观影管理：** 登录、想看和看过、片单、介绍页。到这一步，不带播放的产品已经可以用。
