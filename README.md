# 新版 Moovie

登录后可用的观影管理服务：作品资料来自豆瓣（为主）和 TMDB、IMDb、Wikidata；播放源由用户自己配置，由浏览器直接连接。设计依据和合规红线见 [REBUILD.md](REBUILD.md)。

## 运行

需要 Go 和一个 PostgreSQL（需要 `vector` 和 `pg_trgm` 扩展）。配置写在 `new/.env`，参考 [.env.example](.env.example)；数据库可以写成 `DATABASE_URL`，也可以用 `DB_HOST`、`DB_NAME` 等变量。

```bash
go run ./cmd/web
```

启动时会自动建表。默认同时运行后台任务（元数据采集、AI 语义描述、向量、榜单、豆瓣同步）；设置 `JOBS_IN_WEB=false` 后需要单独运行：

```bash
go run ./cmd/worker
```

第一个注册的账号是管理员。注册要能发邮件：生产环境需要配置 `SMTP_*`（见下面的"邮件"），开发环境不配时邮件内容会打印在日志里。

正式部署用 Docker：见 [deploy/README.md](deploy/README.md)（`Dockerfile`、`docker-compose.yml`、`update.sh`）。

## 导入旧版的影视元数据

新系统是从头开发的，和旧版唯一的联系是旧版积累的公共数据：采集过的影视元数据（作品资料、外部 ID、别名、分集，以及 AI 写的语义描述和向量，新旧生成方式一样，导入后不用重新调用 AI），和众包确认过的广告指纹（连同票数）。账号、标记、短评、片单、进度、弹幕、反馈、屏蔽词都不迁移。

旧库只读；新库的写入在一个事务里完成，出错时整体回滚，可以反复运行。先试运行看报告：

```bash
LEGACY_DB_NAME=moovie_v2 go run ./cmd/migrate-legacy -dry-run
```

确认后去掉 `-dry-run` 正式导入。作品 ID 保持不变，所以要在新库还没有作品时导入（上线前）。

## 临时：示例订阅

为了让老用户切过来时有源可用，临时在 `/sub/example.json` 提供一份示例订阅，内容是旧版保存的播放源；设置页的播放源一栏会出现"使用示例订阅"，点一下就填好并读取。之后会删掉。

```bash
LEGACY_DB_NAME=moovie_v2 go run ./cmd/migrate-legacy -sources data/example-sources.json   # 从旧库导出（只读，不迁移任何数据）
```

然后在 `.env` 里设置 `EXAMPLE_SUBSCRIPTION_FILE=data/example-sources.json` 并重启。同一个地址只留一个（HTTP 的也留着，查询由本站转发），key 用接口的域名。`data/` 已经加进 `.gitignore`。不配置这个变量时，接口返回 404，设置页也没有按钮。

实测（2026-11-17）：旧版 35 个源，设置页检测下来 31 个可用，4 个是对方关站或拦截。

删掉这个功能时一起删：`internal/legacy/sources.go`、`cmd/migrate-legacy` 的 `-sources` 参数、`internal/app/example_subscription.go`（以及 `app.go` 里的路由和 `exampleSub` 字段）、设置页的"使用示例订阅"按钮和 `settings.js` 里对应的几行、配置项 `EXAMPLE_SUBSCRIPTION_FILE`、相关测试。

## 播放源查询的转发

大多数资源站没有给网页跨域许可，浏览器直接查询会被拦下；HTTP 接口在 HTTPS 页面里也访问不了。这类查询由服务器转发：`GET /api/relay?url=…`（`internal/relay`）。

- **只转发订阅文件和查询**（苹果 CMS 的 `ac=detail`，一次请求就带回搜索结果、详情和播放地址），一律走转发，不先试直连。本站自己的地址（比如示例订阅）和本机地址（开发用的模拟源）由浏览器直接访问。
- **视频不转发**：m3u8 和分片仍由浏览器直接加载；视频服务器不允许跨域的线路，hls.js 播不了，会立即换下一个（Safari 用系统播放器，不受影响）。
- **防滥用**：要登录；每个账号每分钟 300 次；同时最多转发 64 个请求；单次最多 2 MB、8 秒；只转文本，视频、播放清单、图片一律拒绝；内容一律当纯文本交回（`text/plain` + `sandbox`），不会以本站身份被当成网页打开；不记录转发的地址。
- **防内网探测**：检查放在建立连接时，本机、内网、链路本地等地址一律拒绝，域名解析到内网或者跳转到内网都会被拦下。代理软件 fake-ip 用的 198.18.0.0/15 放行（这类网络环境里所有域名都解析到这个网段）。

## 添加到桌面

- 教程页：`/install`（不登录也能看），按设备显示 iPhone、安卓、电脑、微信内置浏览器的步骤；安卓 Chrome 和电脑上能一键安装。
- 应用清单 `/manifest.webmanifest`，图标在 `web/static/img`（由旧版的小牛图标生成）。
- Service Worker `/sw.js`：只缓存带版本号的静态文件、断网时显示离线页，不缓存页面和接口，也不经手任何跨域请求（播放源）。
- 前端模块通过 import map 带上版本号，可以长期缓存并并行预加载。
- 全屏打开时：顶部避开刘海和状态栏，二级页面显示返回按钮。
- iPhone 上桌面版和 Safari 不共享登录和本地数据：在桌面版里登录一次，播放源和观看记录会自动同步过来。

## 不登录能看什么

- 能看：首页介绍、发现、搜索作品、作品详情（含相似推荐、短评）、影评、片单、热搜榜、公开的个人主页和月度报告、说明页，以及在线 M3U8 播放器。
- 要登录：播放作品、查源、想看 / 看过 / 评分、发短评和回复、通知、设置、反馈、后台、为你推荐。
- 搜索引擎：每页有 canonical、Open Graph 和 JSON-LD；`/sitemap.xml` 是站点地图索引，涵盖公开页面、资料完整的作品和审核通过的公开片单，`/robots.txt` 排除接口、播放和个人页面。

## 在线 M3U8 播放器

`/m3u8`，不用登录。粘贴 m3u8、HLS 或 MP4 链接直接在同一页播放，是一个常被搜索的工具，所以按落地页来做 SEO：独立的标题和描述、使用说明、常见问题（页面上的问答和 `FAQPage` 结构化数据是同一份）、`WebApplication` 结构化数据、站点地图、页脚链接。

- 链接放在网址的 `#` 后面，服务器收不到；视频由浏览器直接加载。复制分享链接也是这个格式。
- 粘贴一个完整的链接就自动开始播放；也可以把链接拖到播放器上。
- 最近播放的 10 个链接和各自的进度只存在本机（`localStorage`），再次打开从上次的位置继续；能播起来的链接才会记下。
- 播放清单返回 4xx 时立即提示"链接过期或对方不允许"，不再等超时；HTTP 链接会先换成 HTTPS 试一次，不行就说明原因。
- 和作品播放共用同一个播放器：自适应缓冲、慢线路提示、倍速、画中画、手势、快捷键、广告跳过。游客也能跳过大家确认过的广告（指纹列表公开），但投票要登录。

## 热搜榜

`/trends`，有"今天"（最近 24 小时）和"本周"（最近 7 天）两个榜；搜索页显示本周前 10 名。

- **怎么记**：用户在搜索页停下来 1.5 秒、作品库里有结果，浏览器才上报一次（`POST /api/search-log`，每个 IP 每分钟最多 30 次）。同一个人（登录用户按账号，游客按 IP）10 分钟内同一个词只算一次。
- **怎么存**：`search_counts` 每天每个词一行（日期、规范化的词、显示用的写法、次数），不存是谁搜的，也不保存每一次搜索，所以行数取决于每天有多少个不同的词，和搜索次数无关。计数先在内存里累加，每分钟用一条语句批量写入（已有的词加上新的次数）；服务停下时再写一次。保留 31 天（后台概览要画 30 天的搜索趋势）。
- **怎么排**：同一个词的不同写法合并计数，显示最近一天里的写法。库里只有按天的计数，"最近 24 小时"用滑动窗口近似：今天的全部 + 昨天的数 ×（今天还没过去的比例），"本周"同理。至少 2 次才上榜，命中屏蔽词的不上榜。和上一个同样长度的时间段比：以前没有的标"新上榜"，次数达到上次的 1.5 倍以上标"上升"。热度条按榜首的比例画。

## 热门榜

首页和发现页的电影、剧集、综艺、动漫四个榜，每 6 小时重新生成一次，结果整批写进 `chart_items`。每一类综合三个来源，每部作品的分数 = Σ 权重 ÷ (20 + 名次)：

| 来源 | 权重 | 说明 |
| --- | --- | --- |
| 豆瓣热门 | 0.5 | 电影：热门电影；剧集：国产剧和美剧交替合并；综艺、动漫：各自的榜单。最贴近国内观众，作为主体 |
| TMDB 一周趋势 | 0.2 | 只分电影和剧集两个榜，剧集趋势里的作品按作品库里的类型分到剧集、综艺、动漫。只算作品库里已有的（按 `tmdb_id` 对应，一部剧取最新一季），不会因此去请求豆瓣 |
| 本站热播 | 0.3 | 最近 7 天看的人数（`playback_positions`，同一个人看多少集都只算一次）。最近 7 天看过东西的人少于 20 时不计入，免得两三个人就能把一部片子顶上榜 |

- 只用名次，不用各家的评分或热度值：那些数没法放在一起比。"20 + 名次"让前几名之间拉开差距，又不会让单一来源的第一名压过同时出现在几个来源里的作品。
- 每个榜取前 50 部。某一类的豆瓣榜取不到时这一类保持原样；TMDB 取不到就这次不算它。
- IMDb 没有免费的热门接口，只用来对应作品，不作为热度来源。

## 人机校验

登录和注册用工作量证明：页面打开就开始在 Web Worker 里算，用户填完表单时通常已经算完，不需要额外操作。难度由 `POW_BITS` 调整（默认 20，手机上大约 1～3 秒）。测试里用 `Options.DisablePoW` 关掉。

## 邮件

只发和账号有关的邮件，不发通知和营销邮件（`internal/mail`）。

- **注册**只填邮箱：服务器生成一个随机密码（`xxxx-xxxx-xxxx`）发到邮箱，用户用它登录。能收到密码就证明邮箱是对的，所以不需要单独的激活步骤。用户名取自邮箱 @ 前面的部分，可以在设置里改。发信失败时账号会被删掉，可以重新注册。
- **找回密码**：发一个 30 分钟有效的链接。链接的签名里带着当前的密码哈希，密码一改就失效，所以只能用一次，不需要存令牌。没注册过的邮箱也显示同样的结果，避免被用来试探谁注册过。
- **改邮箱**：先给新邮箱发确认链接（24 小时有效），点开后才生效，同时提醒旧邮箱。
- **管理员兜底**：后台"用户"页可以给某个账号生成重置链接，邮件收不到时通过别的渠道发给用户。

收件域名检查（只用标准库）：

- 域名必须有 MX 记录才算能收信。域名不存在、没有 MX、Null MX（只有一条 `.`，RFC 7505）、单段域名（如 `localhost`）、IP 地址都拒绝。
- DNS 超时或网络出错时放行，不误伤正常用户。查询超时 3 秒。有结论的结果缓存 1 小时，临时故障不缓存。
- 中文域名需要先转成 punycode，标准库做不了，直接放行。

防刷：

| 层 | 规则 |
| --- | --- |
| 人机校验 | 注册、找回密码都要过工作量证明 |
| 入口检查 | 注册、改邮箱时当场检查格式和收件域名，提示"该邮箱域名无法接收邮件，请检查是否拼写错误"；这一步不占发信次数 |
| 每个 IP | 每小时最多触发 10 次发信 |
| 每个收件人 | 两封之间至少隔 1 分钟，24 小时内最多 5 封 |
| 全站 | 每小时最多 `MAIL_HOURLY_LIMIT` 封（默认 200） |
| 发信层兜底 | 所有邮件发送前都再查一次收件域名，收不了信的跳过并记日志 |

"邮箱已修改"这类安全提醒不受单个收件人的限制（只受全站上限），免得有人先刷满对方的次数，让提醒发不出去。发信记录表 `mail_log` 只存收件人邮箱的 SHA-256，保留 35 天（后台趋势图看最近 30 天的发信量）。

## 通知

站内通知：有人赞了或回复了你的短评、有人关注你、**管理员回复了你的反馈**、**管理员删除了你的短评或回复**（附原因和被删内容的摘要，可以去反馈页申诉）。导航栏有未读红点。打开通知页不会自动已读：点开一条会标为已读并跳到相关页面；每条可以单独"已读"或删除，也可以"全部已读""清空"。不发邮件通知。

管理员可以在短评下面直接删除别人的短评（评分和看过记录保留，回复和点赞一起删掉），删除时要填原因。

## 分享卡片

作品详情、短评、片单、月度报告都可以生成分享图片（1080×1440，带二维码），用于微信、朋友圈、小红书。图片由浏览器用 canvas 画（`web/static/js/core/sharecard.js`），服务器只在页面上提供文字和图片地址（`data-card`），不需要中文字体和图片处理。手机上可以直接分享图片（系统支持时）或长按保存，电脑上可以下载。主页没公开时，报告卡片上的二维码指向首页。

## 导出数据、注销账号

- **导出**（设置 → 我的数据）：`/settings/export.json` 是全部数据（账号、想看和看过、评分、短评、回复、进度、弹幕、关注、反馈）；在网页上点按钮时，浏览器会把本机解密的加密历史附进 `private_history`。`/settings/export.csv` 只有想看和看过，带 BOM 方便 Excel 打开，用户写的内容以 `= + - @` 开头时加 `'`，防止被表格当公式执行。
- **注销**（设置 → 注销账号）：要输入当前密码和“注销”两个字。账号和数据随外键级联删除；反馈保留但不再关联到人。管理员名下的片单转给另一位管理员；唯一的管理员不能注销。注销后浏览器清掉这个账号在本机的数据（订阅地址、密钥、本地历史），并给本人发一封确认邮件。后台删除用户走同一套逻辑。

## 上线前：发信检查

1. 在 `.env` 配好 `SMTP_HOST`、`SMTP_PORT`、`SMTP_USER`、`SMTP_PASS`、`SMTP_FROM`，发件域名配好 SPF、DKIM、DMARC（在邮件服务商的后台能拿到要加的 DNS 记录）。版权投诉页公布的联系邮箱是 `CONTACT_EMAIL`，不配时用发件人地址。先只连接、登录，不发信：

```bash
go run ./cmd/mailcheck -dial
```

2. 给几家常用邮箱各发一封测试邮件，确认在收件箱（不是垃圾邮件），邮件头里 SPF、DKIM、DMARC 都是 `pass`：

```bash
go run ./cmd/mailcheck -to 你的QQ邮箱
```


## 数据库里有哪些表

一共 24 张业务表（另有一张迁移记录表）：[internal/db/migrations/0001_init.sql](internal/db/migrations/0001_init.sql)，短剧加的列和索引在 [0002_short_drama.sql](internal/db/migrations/0002_short_drama.sql)。
留下来的标准是：**别处推不出来、又确实有人读**。能算出来的现算，只写不读的不存。

| 用途 | 表 | 为什么需要 |
| --- | --- | --- |
| 账号 | `users`、`user_follows`、`keyrings` | 账号本身；关注关系；登录即同步用的密文 |
| 作品资料 | `media`、`media_aliases`、`media_units`、`chart_items` | 作品；别名用来匹配资源站片名和搜索；分集用来显示集名和"今日更新"；豆瓣榜单 |

| 运营 | `blocked_keywords`、`search_counts`、`mail_log`、`image_mirrors`、`jobs` | 屏蔽词；每天每个词的搜索次数；发信限流；图片在 Telegram 的文件编号；后台任务队列 |

`media` 上和采集有关的列：`metadata_synced_at`（豆瓣或红果同步时间）、`enriched_at`（Wikidata / TMDB 补充时间）、`semantic_text` 和 `semantic_hash`（AI 写的描述和所用资料的哈希）、`embedding`（向量）。失败次数、冷却期这些不另外存，看 `jobs` 表里的失败记录就够了。

关于 schema：正式运行时不设置 `DB_SCHEMA`，表建在 `public` 里。演示数据用 `DB_SCHEMA=mv_demo` 单独放一个 schema，是为了 `go run ./cmd/devseed -reset` 可以整个删掉重建而不碰别的数据；测试也是每个包一个临时 schema。`public` 里目前只有 `vector` 和 `pg_trgm` 两个扩展。

## 搜索引擎优化

不登录能看的页面都带 canonical、Open Graph 和结构化数据；登录后才有的页面一律 `noindex`。

- **作品详情**：标题是"片名（年份） - 类型简介、演员表、短评"；描述由导演、主演、类型、豆瓣评分和简介拼成；结构化数据包含面包屑。电影使用 `Movie`，单季页面使用 `TVSeason`，通过 `partOfSeries` 关联整剧及其 IMDb、TMDB 对应条目。
- **内容直接写在页面里**：没登录的访客（包括爬虫）打开详情页时，短评和相似推荐由服务器直接输出，不是滚动到附近才加载。很多爬虫（比如百度）不执行脚本，这样它们读得到内容，也能顺着链接发现其他作品。登录用户仍然是懒加载。
- **不收录但跟踪链接**（`noindex,follow`）：带关键词的搜索结果、"相似作品"列表、资料还没补全的作品、个人主页和观影报告。
- **片单广场和公开片单**使用 `CollectionPage`、`ItemList` 和面包屑。广场分页使用各自的 canonical。热门排序、仅链接可见的片单和空片单用 `noindex`。**首页**使用 `WebSite`（站点名称）。
- `robots.txt` 指向 `/sitemap.xml`。索引列出公开页面、作品和片单的子地图。作品和片单按固定 ID 范围分片，并附页面更新时间。
- 图片：首屏的大图和 logo 立即加载（懒加载会让首屏变慢），其余全部 `loading="lazy"`；详情页的海报和剧照有描述文字（alt）。

## 登录即同步

换设备、换浏览器（包括 iPhone 的桌面版）登录同一个账号，播放源和加密的观看记录就都在，不需要扫码配对（`web/static/js/core/keyring.js`）。

- 设备主密钥和订阅地址合成一个"钥匙圈"，在浏览器里用登录密码经 PBKDF2-SHA256（31 万次）派生的密钥加密（AES-GCM），密文存在 `keyrings` 表。服务器只有密文、随机盐和迭代次数。
- 需要浏览器支持 Web Crypto；正式环境用 HTTPS，本机开发可用 localhost。普通局域网 HTTP 地址不能加密同步时会明确提示，不再把本机保存说成账号保存成功。
- 登录改为脚本提交：成功后趁密码还在内存里解开钥匙圈，写进本机；账号还没有钥匙圈时，用这台设备的建一个。这台设备之前用的是另一把密钥时，本机的观看记录会用账号的密钥重新加密。登录后的同步失败会留在页面显示错误，用户仍可点击进入网站；不再用 12 秒跳转中断尚未完成的同步。
- 保存订阅的顺序是校验订阅 → 加密上传 → 数据库确认 → 本机生效 → 提示“已保存到账号”。清除也必须等待后端确认；失败时保留原配置和待重试的输入，并显示加密不可用、未解锁、网络、认证、版本冲突或服务端错误。旧版本只存在本机的订阅会保留，并提示手动保存到账号。
- 其他设备打开页面时（成功检查后 5 分钟内不重复检查）拉取更新；失败不会提前标记同步完成，设置页收到更新后会重新显示列表。远端明确清除订阅时，本机的旧订阅不会反向覆盖账号配置。
- 改密码前先生成新密码对应的密文，与新密码一起提交。服务端在一个事务内更新密码、会话版本和加密配置，版本冲突或写入失败全部回滚，成功后才更新本机密钥。找回密码后，持有旧包装密钥的原设备可以用新密码登录恢复；新设备解密失败时会提示恢复方法，不会用空配置覆盖账号原数据。
- 取舍：服务器不保存密码，但每次登录时会短暂收到密码（所有网站都一样），理论上可以据此派生出密钥。比起之前"订阅只在本机"，这一点上弱了一些，换来的是不用扫码。

## Telegram 图床

配置 `TELEGRAM_BOT_TOKEN` 和 `TELEGRAM_CHAT_ID` 后（存到频道、群，或者最简单的：和机器人的私聊——给机器人发一句 /start，不填 `TELEGRAM_CHAT_ID` 运行 `go run ./cmd/tgcheck` 就能看到自己的 chat_id；私聊每秒能存一张，频道和群每分钟约 20 张），图片代理（`/img/…`，豆瓣、TMDB 的图片和红果短剧的封面都走这里）会把代理过的图片备份到 Telegram 频道（`internal/imageproxy/mirror.go`、`internal/telegram`）：

- 第一次回源完整读取图片并检查大小后返回，再把同一份内容交给备份器，不为上传重复下载。应用不缓存图片内容，浏览器和 CDN 负责缓存；当前请求和待上传队列里的临时数据不作缓存使用。
- 新文件按 `片名_海报或剧照_缩略图或展示图或原图_短哈希.扩展名` 命名，组合封面和月报海报也保留各自作品的片名。相同来源尺寸共用备份，不按页面重复上传；旧文件名不变，已有备份仍可读取。
- 备份器在网站进程后台逐张用 `sendDocument` 上传所选规格的文件内容，Telegram 不再额外压缩。频道每 3.2 秒一张、私聊每 1.1 秒一张，被限流时按 `retry_after` 等待后再传。排队的数据最多 32 MB，上传失败后一小时内不再排；进程重启丢了也没关系，下次有人看到会重新排。
- `image_mirrors` 表保存原图地址、Telegram 的文件编号（`tg_file_id`，取图只需要它）、类型和大小。
- 之后的请求优先从 Telegram 取：程序用 `getFile` 换出下载地址（缓存 50 分钟）再转给浏览器，浏览器看不到机器人的 token。Telegram 取不到时退回原图。
- 后台概览显示已备份的数量和大小。用 `go run ./cmd/tgcheck` 检查机器人和频道（只读，不发消息）。
- 服务器要能访问 api.telegram.org；访问不了时可以用 `TELEGRAM_API_BASE` 换成自建的反向代理。

图片链接由应用签名，`size` 只支持 `thumb`（列表和剧照预览）、`display`（详情和横幅）、`original`（点开剧照）。片名、用途、来源地址和规格都在校验范围内，旧的无签名代理入口不再接受。页面、SEO 和分享卡片使用同一个签名器，地址不绑定登录、IP，也不按时间过期，便于 CDN 缓存和搜索抓取。签名使用 `APP_SECRET` 派生的独立密钥，修改 `APP_SECRET` 后要刷新 CDN 的旧页面缓存。

优先使用来源提供的尺寸：TMDB 海报用 w342 / w780，剧照用 w780 / w1280，原图用 original；豆瓣用中图 / 大图；红果缩略图用 320 宽，其余保留来源版本。来源没有尺寸接口或缺少某张图的尺寸版本时，在当前请求中用纯 Go 缩图，最多同时处理 2 张，最长边为 480 / 1280，保持比例、不放大，透明图保留 PNG；支持 JPEG、PNG、GIF（缩图取首帧）、WebP，不增加系统图像库依赖。原图保留来源提供的文件，豆瓣、红果不保证能提供未缩放的母版。TG 自动缩略图是可选预览，本实现不依赖它。

成功图片可缓存 30 天并支持 ETag；签名错误、限流、回源错误、超限或读取不完整的图片均返回真实错误状态和 `Cache-Control: no-store`，不返回状态为 200 的错误占位图。每张文件最多 8 MiB，本机解码前检查不超过 1200 万像素。应用只在回源时执行签名、频率和来源域名校验，不根据 Referer / Sec-Fetch-Site 返回不同内容；严格的外站嵌图限制由 CDN 在缓存查找前执行。CDN 配置见 [部署说明](deploy/README.md#图片与-cdn)。

## 豆瓣请求节奏

豆瓣请求之间默认间隔 1 秒。返回 403 / 418 / 429（被限流）时间隔翻倍，最多 1 分钟；连续 3 次被限流就整体暂停 10 分钟，暂停期间的请求直接失败，任务稍后自动重试，页面不会卡住；之后每成功一次，间隔缩回一点。后台概览显示当前的节奏。需要时可以用 `DOUBAN_PROXY`（http / https / socks5）让豆瓣的接口请求走指定的出站代理。

想用买的 Clash 订阅：网站本身不认识 Shadowsocks、VMess、Trojan 这些协议，所以另外跑一个 mihomo（Clash.Meta 内核）容器，把订阅变成一个 HTTP / SOCKS5 代理，再把 `DOUBAN_PROXY` 指过去。`deploy/mihomo/` 里有配置模板和 docker compose 文件：

- 单独的容器、单独的 Docker 网络 `moovie-egress`：不用 host 网络、不建 TUN 网卡、不要额外权限，不向宿主机开放端口，宿主机的网络不受影响。
- 别的容器加入 `moovie-egress` 网络就能用 `http://mihomo:7890`；mihomo 只接受 Docker 内网的连接，也可以再加用户名密码。
- 节点放在一个轮询的负载均衡组里，连续的请求从不同的节点出去；健康检查用通用地址，不额外打扰豆瓣。填了订阅链接的 `config.yaml` 已经加进 `.gitignore`。

## 元数据采集

### 什么时候采集

| 入口 | 什么情况下 | 优先级（越大越先做） |
| --- | --- | --- |
| 打开详情页 | 这部作品还没从豆瓣同步过。已经排在队尾的会被提到最前面 | 20 |
| 管理员 | 按豆瓣 ID 添加作品，或者点"刷新"。不管冷却期，四步整条重跑 | 10 |
| 热门榜单 | 每 6 小时刷新一次，榜单里新出现的作品 | 5 |
| 站内搜索 | 作品库里不到 3 个结果时，去豆瓣查联想（同一个词一天一次），查到的新作品 | 5 |
| 浏览器匹配片名 | 用户的资源对不上作品库、但带了豆瓣 ID（每个账号每分钟最多 20 个） | 5 |
| 导入豆瓣标记 | 用户点"同步"是完整同步（优先级 5）；每天自动的那次是增量同步（-2），读到整页都已导入就停 | — |
| 导入带来的新作品 | 列表里已经有片名、海报和评分，晚点补全不影响使用 | 0 |
| 每小时巡检 | 四步里漏掉的都补上（见下） | -1 / -2 |

### 一部作品的四步

每一步是一个单独的任务，成功了马上保存、再排下一步；失败了只重试这一步，不会让前面的步骤重来。

1. **豆瓣**（`media.refresh`）：片名、年份、简介、类型、地区、导演、主演、评分、海报、又名。已知是电影还是剧集时先试对应的接口，猜对了只发一次请求。豆瓣确认没有这个条目（两个接口都是 404）就记成 `not_found` 并隐藏，以后从任何入口送来都不再请求。
2. **Wikidata、TMDB**（`media.enrich`）：Wikidata 按豆瓣 ID 精确对应，给出 IMDb、TMDB 编号和各语言片名；TMDB 给剧照、分集、连载状态，豆瓣没有的简介、原名、片长也用它的。找 TMDB 条目的顺序：已存的编号 → 用 IMDb 编号反查 → 片名加年份搜索。
3. **AI 写语义描述**（`media.semantic`）：把资料发给大模型（OpenAI 格式的 `/chat/completions`），写成一段 200 字以内、语义密度很高的描述，保存到 `semantic_text`。提示词和资料格式和旧版一字不差（`internal/ingest/prompt.go`、`media.SemanticInput`），因为迁移过来的描述就是这样写的。`semantic_hash` 记着写描述时所用资料的哈希：资料没变就不再调用 AI。
4. **算向量**（`media.embed`）：用语义描述算 768 维向量（OpenAI 格式的 `/embeddings`，默认模型 `quentinz/bge-base-zh-v1.5`，和旧版一样）。描述改写了，旧向量随之清空重算。

描述和向量分开保存：AI 成功、向量失败时，描述留着，重试向量不会再调用一次 AI。没配 AI 时不写描述，新作品也就没有向量，相似推荐改按类型重合度。

### 失败了怎么办

- 重试间隔逐次加长：1 分钟、10 分钟、1 小时、6 小时、1 天，共 6 次（约 31 小时）。用完标记为失败。
- **冷却期**：失败记录保留 14 天，这期间这部作品的这一步不会再被任何入口排进来（管理员手动刷新除外），一个一直出错的作品不会被反复送去请求对方。成功一次就清掉失败记录。
- Wikidata 或 TMDB 出错只算第 2 步失败，豆瓣不会再被请求；重试用完时照样往下写描述，过了冷却期由巡检再补一次。
- 豆瓣限流（403 / 418 / 429）：任务放回队列一分钟后再做，不算失败；连续被限流时整条豆瓣通道暂停 10 分钟，任务原样等着。入队超过 3 天的任务再被限流就按普通失败算，免得某个条目一直被拒绝、永远在队列里转。

### 巡检挑哪些作品

- 第 1 步：从没同步成功过的；连载中的剧集每天一次（TMDB 标了连载中，或者没标状态但是近两年的）；近两年上映的每周一次（评分还在变）。更早的同步一次就够了。
- 第 2 步：豆瓣同步过、这一轮还没补到 Wikidata / TMDB 资料的。
- 第 3 步：资料够了（有片名和简介或原名）、还没有语义描述的。正在补第 2 步的先不挑，免得 AI 按不全的资料写一遍、补完又写一遍。
- 第 4 步：有描述、没向量的。
- 正在排队、运行或处在冷却期的作品都不挑，一批一直失败的作品不会每次都排在最前面、把别的挤掉。

### 豆瓣 ID 的过滤

- 格式：7–9 位数字，不以 0 开头（豆瓣的条目编号从 100 万开始，旧版里是 129 万到 3854 万）。不合格式的不收录，也就不会拿去请求。
- 豆瓣确认没有的 ID（比如图书、音乐的条目）永久记住，不再请求。
- 一直出错的 ID：6 次重试用完后冷却 14 天。

### 执行通道

- 豆瓣通道：3 个执行位，所有豆瓣请求共用每秒一次的限速。补豆瓣资料、刷新榜单、同步用户标记都走这里。
- AI 通道：2 个执行位。写一段描述要十几秒到一分钟，不让它堵住别的任务。
- 红果通道：2 个执行位，共用每秒一次的限速，只做短剧的任务（见"短剧"）。
- 默认通道（`WORKER_CONCURRENCY`，默认 2）：Wikidata / TMDB、算向量、巡检、清理。

后台概览显示还有多少作品在等、最早的等了多久、照现在的速度大约多久做完。完成的任务记录保留 3 天。重启不会把周期任务（榜单、巡检、每日同步）立刻再跑一遍。

## 短剧

短剧的资料只来自红果短剧官网（hongguoduanju.com），和电影、剧集放在同一张 `media` 表里（`media_type = 'short'`），所以想看、播放进度、片单、短评都能直接用。

### 从哪里取

只读官网公开给搜索引擎的页面（robots.txt 允许）：站点地图、详情页、榜单、分类页。这些页面是服务端渲染的，资料在页面里的 `_ROUTER_DATA` JSON 里，直接按 JSON 读（`internal/providers/hongguo.go`）。站内搜索不用：`/query/` 已经停用，`/search` 的结果要经过字节的风控签名。

| 页面 | 拿到什么 |
| --- | --- |
| 详情页 `/detail?series_id=` | 片名、简介、封面、题材标签、演员（大多是空的）、已上线集数和总集数、是否完结、上架时间、系列 ID（各季共用）、评分、热度 |
| 站点地图 `/sitemap/hongguoduanju/index.xml` | 31 个子文件，约 65 万个 series_id（2026-11-18 实测 649366 个）；支持 gzip 和 ETag |
| 重点剧目 `/seo-important.xml` | 约 2000 部热门（里面的 lastmod 不可信，只当名单用） |
| 榜单 `/rank/hot-drama`、`/rank/new-drama`，分剧种的 `/rank/hot-comic-drama` 等 | 名次；卡片标签里有剧种 |
| 分类页 `/category/real-drama`、`comic-drama`、`ai-drama` | 剧种。每个剧种最多 800 部（34 页） |

不取的：视频 ID 和播放地址（不是元数据）、红果用户的评论（别人的用户内容，带用户名和头像）。

**剧种**（真人剧、漫剧、AI剧）详情页不给，只有分类页和分剧种的榜单给，所以只有比较热门的几千部知道剧种。知道的作为一个值放在 `genres` 最前面，题材和剧种一起用 `genres @> ARRAY[...]` 筛选。

### 全量：本地抓一次再导入（教程）

全量约 65 万部，按每秒一次要抓七八天。这一次在自己的电脑上做：不占线上的执行位，万一被风控也只影响本机的 IP。线上程序只做增量，导入以后自动接上。

**1. 先小规模试一下**（一两分钟），确认网络通、能抓到资料：

```bash
cd new
go run ./cmd/hongguo-seed crawl -important -limit 20 -o data/hongguo-try.jsonl
```

打开 `data/hongguo-try.jsonl` 看看，每行是一部短剧的 JSON。试完可以删掉这个文件。

**2. 开始全量抓取。** 找一个终端窗口一直开着（Mac 上加 `caffeinate -i`，防止电脑睡眠时中断）：

```bash
cd new
caffeinate -i go run ./cmd/hongguo-seed crawl
```

- 先读三个剧种的分类页和分剧种的榜单（一百来次请求，记下约 2400 部的剧种），再读 31 个站点地图拿到全部 series_id，然后逐部抓详情，抓到一部往 `data/hongguo.jsonl` 写一行。重点剧目（热门的约 2000 部）排在最前面。
- 每 200 部打印一次进度和预计剩余时间。
- **随时可以按 Ctrl-C 停下**，再运行同一条命令就接着抓：已经写进文件的跳过，上次被强行打断写了半行的会自动截掉。关机、断网都没关系。
- 被限流时自动放慢；连续被限流会暂停 10 分钟再继续，不用管它。抓失败的不写进文件，下次运行时重试。
- 想慢一点（更不容易被风控）就加 `-interval 2s`，时间会翻倍。
- 文件大约 500 MB（一部短剧不到 1 KB），`data/` 已经在 `.gitignore` 里。

**3. 先导入本地的测试 schema 看看**（不碰正式数据）：

```bash
cd new
DB_SCHEMA=mv_live go run ./cmd/hongguo-seed import
```

导入时按 series_id 有则更新、无则插入，可以反复运行；确认不存在的 ID 也建一行、记成 `not_found` 并隐藏，这样线上对比站点地图时不会把它们当新剧再抓。几十万部大约要十几分钟到半小时（`-workers 8` 是同时写库的连接数）。导入完打开 `/discover/short` 和管理后台的概览，看短剧的数量对不对。

**4. 导入正式库。** 两种方式选一种：

把文件拷到服务器上，用镜像里的命令导入（`new/data` 挂载在容器的 `/app/data`）：

```bash
scp new/data/hongguo.jsonl 服务器:部署目录/data/
```

```bash
docker compose run --rm --no-deps web ./hongguo-seed import -i data/hongguo.jsonl
```

或者在本地通过 SSH 隧道直接写正式库（`DATABASE_URL` 指向隧道的本地端口）：

```bash
ssh -N -L 15432:数据库地址:5432 服务器
```

```bash
cd new
DATABASE_URL=postgres://用户:密码@127.0.0.1:15432/库名 go run ./cmd/hongguo-seed import
```

**5. 导入以后。** 什么都不用做：线上的增量任务每天会刷新榜单和重点剧目、收录新上架的剧、更新连载中的剧（见下）。想马上看到榜单，在管理后台概览点"刷新短剧榜单和重点剧目"。

以后想整体重新校对一遍（比如过了半年），重新抓一份新文件再导入即可：`go run ./cmd/hongguo-seed crawl -o data/hongguo-2027.jsonl`。

### 线上的增量

`HONGGUO_SYNC=false` 可以关掉下面的定期任务（单部短剧的刷新仍然有：资料还没抓到时有人打开，就去抓一次）。

| 任务 | 频率 | 内容 |
| --- | --- | --- |
| `hongguo.lists` | 每天 | 热播榜、新剧榜各读前 3 页（60 部），前 50 部生成短剧频道的两个榜单（`chart_items` 的 `short_hot`、`short_new`），上榜的剧都刷新一次；分剧种的榜单补剧种；重点剧目约 2000 部全部刷新（热度、评分、集数） |
| `hongguo.categories` | 每周 | 三个剧种的分类页，补剧种 |
| `hongguo.sitemaps` | 每天 | 读全部子站点地图（没变化的回 304，不重新下载），和作品库对比，新的 series_id 收进来。从新到旧每天最多 3000 部：导入过快照时每天的新剧远少于这个数；没导入时不会一下子排几十万个任务 |
| 每小时巡检 | 每小时 | 没抓到过的、连载中一天没更新的短剧重新抓（最多 300 部）。已完结的不再抓 |

站点地图的 ETag 只放在内存里，重启后重新下载一遍（压缩后十几 MB），不为它建表。一个子文件里的新剧全部收进来以后才记下它的 ETag，没收完的第二天照样重读。

### 怎么展示

- **短剧频道** `/discover/short`：剧种、题材两排筛选（题材是最热的 5000 部短剧里最常见的 20 个标签，一小时统计一次）；按热度、红果评分、上架时间（series_id 随时间递增，倒序就是最新的）排序；没有筛选时顶上是热播榜和新剧榜。
- **其他浏览入口不出现短剧**：发现页的"全部"、首页推荐的兜底榜单、长剧的相似推荐都排除短剧；短剧的相似推荐也只推短剧（按题材重合度，先按热度取前 500 部有共同题材的，再按重合度排）。
- **搜索**：短剧和其他作品一起搜，同样匹配时短剧排在后面，卡片上写着"短剧 · 题材"。
- **详情页**：显示剧种、红果评分、"全 80 集 / 更新至第 30 集"，信息栏链接到红果的原页面。
- **不让搜索引擎收录**：短剧详情页和短剧频道都是 `noindex`，也不进本站的站点地图。简介是从红果原样来的，收录了也排不过官网。
- 短剧不写 AI 描述、不算向量，不补豆瓣、TMDB、Wikidata。
- 封面在字节的图床（`p*-novel.byteimg.com`）上，走站内签名图片代理：列表请求 320 宽的缩略图，展示和原图保留来源版本。和豆瓣图片一样：有人看到时备份到 Telegram，之后优先从 Telegram 取。

### 数据量大以后的查询

短剧会比其他作品多两个数量级，凡是要扫 `media` 的查询都按类型走各自的索引（`0002_short_drama.sql`）：

- 长剧的后台巡检（豆瓣、补资料、AI 描述、向量）和本站站点地图都带 `media_type <> 'short'`，走 `media_long_idx`，不碰短剧那几十万行。
- 短剧频道按热度走 `media_short_heat_idx`，按上架时间走 `hongguo_id` 的唯一索引；题材、剧种筛选走 `genres` 的 GIN 索引。
- 短剧的巡检走 `media_short_sync_idx`，里面只有没抓过的和连载中的，已完结的不在索引里。

## 管理后台

`/admin`，只有管理员能进（第一个注册的账号是管理员；电脑上顶部导航有"管理"，手机上在"我的"页底部）。

| 页面 | 做什么 |
| --- | --- |
| 概览 | 各项数字（含短剧总数、资料完整的、待抓的）；外部服务（豆瓣和红果的请求节奏、TMDB、AI、向量、发信、Telegram 图床）是否正常；还有多少作品和短剧在等采集；手动刷新热门榜、短剧榜单和重点剧目、收录新上架的短剧；最近 30 天每天的新用户、观影人数、新标记、回复、弹幕、搜索、发信 |
| 用户 | 搜索、设管理员、生成重置密码链接、删除；**禁言**（不能发短评、回复、弹幕，其他照常，会收到通知）和**封禁**（不能登录，立即踢下线），可以选 1 / 7 / 30 天或永久，要写原因。管理员不能被限制 |
| 作品 | 按"电影、剧集、综艺、动漫"和"短剧"分开看（短剧会比其他作品多两个数量级）；搜索框可以填片名、豆瓣 ID，或者直接粘贴豆瓣、红果的链接；添加作品同样认豆瓣 ID / 链接和红果链接（用户反馈搜不到某部短剧时用）；同步、隐藏 |
| 片单、反馈、屏蔽词、任务 | 和之前一样 |
| 内容审核 | 最新的短评、回复、弹幕，可以按内容或用户名搜，批量删除；删短评和回复时作者会收到通知（附原因） |
| 广告指纹 | 只读：每个指纹的确认票、否认票、状态、最早出现和最近投票时间，用来发现异常。不提供人工裁定——管理员看不到画面，没有依据判断；是不是广告由看到画面的人投票（疑似广告时的询问、自动跳过后"撤销 → 这段不是广告"） |

## 广告跳过

用 hls.js 播放时，分析的是 hls.js 实际加载的那一份播放清单（通过 `pLoader` 观察，不修改），分片路径按跳转之后的最终地址解析，切换清晰度时换成那一路的分析结果；这和旧版的做法一致，众包指纹通用。Safari 用系统播放器时看不到它加载的清单，只能另外下载一份分析（同样按最终地址解析）。

## 慢线路

- 缓冲往前多攒（最多 60～180 秒），分片下载超时放宽到 40 秒，慢但在下载的分片不会被反复中断。
- 边播边算当前线路的倍速（每秒能下载几秒视频）；连续 3 个分片低于 1.3 倍时，试探其他线路（下载清单和第一个分片的开头，最多 1.5 MB，一分钟最多一次），有明显更快的就提示，点"切换线路"才换。卡住超过 8 秒也只提示，不自动换。
- 往前缓冲多少按情况调整（只对 hls.js 有效，Safari 的系统播放器自己决定）：线路快（2 倍速以上）时 60 秒；线路勉强够用（不到 2 倍速）时边播边攒到 3 分钟，扛住更长的网速低谷；暂停时攒到 5 分钟。线路比视频码率还慢时缓冲多少都会被耗光，靠提示换线路。

## 已知限制

- 豆瓣的抓取、TMDB 和 Wikidata 的同步只用假服务器测过，没有对真实接口跑过完整流程。
- 第三方弹幕库（dandanplay 协议）只用假服务器测过。
- 没有在真机上测过 iPhone 的系统播放器、触屏手势、长按三倍速和锁定按钮，也没有测过 AirPlay。
- 没有用真实的 SMTP 服务器发过信，只用假的邮件服务器测过；正式上线前要配好 SPF、DKIM、DMARC 再实测各家邮箱（QQ、163、Gmail、Outlook）能否收到。
- 分享卡片只在 Chromium 里看过效果，没有在 iPhone Safari 和微信内置浏览器里实测；TMDB 的海报跨域加载失败时卡片上会是占位色块。
- 慢线路的测速和自动换线只在本机演示环境里跑过，没有在真实的慢源上验证效果。
- "原来的源还在，但视频都播放不了"时换源的流程只看过代码，演示源模拟不了这种情况，没有在浏览器里走过。
- 第三方下载链接指向外部网站，那个网站能不能用、会不会改地址，本站控制不了。
- Service Worker 只在模拟环境里测过（开发用的内置浏览器不允许注册），没有在真机上验证过安装流程。
- Chrome 的控制台偶尔会出现一条 `Transition was aborted` 的报错：这是浏览器在预渲染页面和页面过渡动画同时生效时自己打的，不影响使用。
